# 分块策略

## 为什么要分块

整篇文档塞进提示词有三个问题：太长、太贵、太散。

太长的文档会挤掉对话历史；按 token 计费时整篇文档的成本是分块的几十倍；而且大部分内容和问题无关，会稀释相关信息。

分块的目标是**每块只讲一件事**，这样检索时能精确命中。

## 按标题切分

最朴素也最有效的策略：以 Markdown 的标题层级为边界。

标题天然是语义边界，作者写标题时就是在划分主题。按标题切出来的块，其 heading path 还能直接当 locator 用。

## 块大小怎么定

常见范围是 300 到 1000 个字符。太小会丢失上下文，太大会稀释相关性。

具体数字取决于三件事：

1. 文档密度：技术文档一句一个信息点，可以小一点
2. 问题粒度：用户问的是「这个函数参数是什么」还是「这个模块怎么设计」
3. 模型窗口：窗口越大，块可以越大，但检索精度不会因此变好

## 重叠区

相邻块之间留一段重叠（通常 10% 到 20%），可以避免答案恰好被切在边界上。

代价是索引体积变大、同一段内容可能被重复召回。去重时按 chunk id 去，不要按文本去。

## 常见错误

**按固定字符数硬切。** 会把一句话切成两半，检索命中后模型拿到的是残句。

**块里不带标题。** 用户搜「分块」时，正文里没有「分块」二字的段落会被漏掉。把 heading path 拼进块文本或单独存字段都可以。

**只切不标记。** 切完没有记录起止位置，后面做引用时只能显示「某文档的某段」，用户无法核对。
